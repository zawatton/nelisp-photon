#+title: nelisp-photon

* Overview

~nelisp-photon~ is an Emacs-Lisp / NeLisp implementation of Fujitsu's
*PHOTON* architecture (Parallel Hierarchical Operation for TOp-down
Networks): a non-Transformer, hierarchical autoregressive language-model
architecture that replaces token-by-token "horizontal" scanning with a
multi-resolution, top-down hierarchy, drastically cutting decode-time
KV-cache traffic.

Reference (read before redesigning the core architecture): PHOTON paper,
Ichikawa et al. (to appear at ACL 2026) -- https://arxiv.org/abs/2512.20687

PHOTON's core ideas this repository implements:

- *Bottom-up encoder*: compress tokens into low-rate contextual states,
  forming a multi-level representation hierarchy.
- *Lightweight top-down decoders*: reconstruct fine-grained token
  representations in parallel across the hierarchy.
- *Recursive generation*: update only the coarsest latent stream, avoiding
  redundant re-encoding.
- *Multi-query integration*: generate several candidate continuations and
  consolidate them by voting / best selection.

Concretely, the executable sketch:

- splits tokens into fixed-size chunks
- compresses each chunk bottom-up into a coarse latent state
- runs causal context updates over the coarse states
- decodes each chunk with a bounded local autoregressive decoder
- generates multiple candidates and merges them by voting

Reported PHOTON benefits (Fujitsu / paper): up to ~475x multi-query
throughput per GPU resource and up to ~10^3x higher throughput per unit
memory versus Transformers, with comparable quality.  The win is in the
long-context, multi-query, and multi-agent regimes where Transformer
KV-cache traffic dominates.

Note: a complementary GPT-style dense engine (~photon-tensor~,
~photon-transformer~) and a GPU backend (sibling ~nelisp-gpu~) also live
here as a fast, well-understood baseline and as the tensor/GPU substrate;
the PHOTON hierarchical core above is the architectural identity of the
project.

The implementation deliberately uses simple vector arithmetic and deterministic
pseudo-weights, so the first milestone is inspectable behavior rather than
model quality.  Heavy tensor math can later be moved behind the same function
boundaries.

* Run

#+begin_src sh
make smoke
#+end_src

or directly:

#+begin_src sh
../nelisp/target/nelisp --load examples/run.el
#+end_src

Run a tiny online training loop:

#+begin_src sh
make train
#+end_src

Training and evaluation return both accuracy and a weighted loss breakdown:
~next-token-loss~, ~reconstruction-loss~, and ~next-context-loss~.  Their
weights live in architecture params as ~next-token-weight~,
~reconstruction-weight~, and ~next-context-weight~.  The update rules are still
simple, but all three signals now feed the model: next-token updates the main
head path, reconstruction updates missed decoded positions, and next-context
nudges chunk/context gain and projection parameters.
The next-token readout also has a small exact transition memory and a target
prototype table, kept separate from the trainable output head.

The training example uses a repeated numeric corpus.  ~accuracy-permil~ is an
integer score where 1000 means 100%.

Run a character-level text training example:

#+begin_src sh
make text-train
#+end_src

This builds a small character vocabulary, encodes the text, trains the output
head, and generates text from a prompt.

The character demo also runs on the standalone NeLisp binary, not only
inside Emacs:

#+begin_src sh
../nelisp/target/nelisp --load examples/text-train.el
#+end_src

To stay loadable there, ~photon.el~ carries a small portability layer,
all guarded so real Emacs keeps its native versions: pure-elisp ~exp~,
~log~, ~random~, and ~sxhash~ (used by softmax, the log-sum-exp
perplexity, and the seeded sampler), plus model/vocab/history persistence
that writes with ~prin1-to-string~ and reads through the O(n) file loader
instead of ~(prin1 ... (current-buffer))~ / ~(read (current-buffer))~.
The standalone runtime exposes no ~current-buffer~ and its
~read-from-string~ is quadratic on multi-KB input, so the loader wrapper
keeps model loading linear.  With these in place a NeLisp run trains the
repeated ~"ab ab"~ corpus to held-out accuracy 1000 permil and generates
from a prompt in both greedy and seeded-sample modes, including through
~examples/photon-cli.el~ (~make photon-cli-generate~).

Run the batch/checkpoint/resume training path:

#+begin_src sh
make batch-train
#+end_src

This loads a text corpus through the batch dataset loader, uses fixed-context
training pairs with a train/eval split, deterministic shuffle, mini-batch
output-head updates, epoch eval snapshots, epoch checkpoints, saved training
history, and resume loading.  With ~history-path~, resume continues from the
next epoch number instead of overwriting the previous run history.

Run a configurable longer batch loop:

#+begin_src sh
make serious-train
PHOTON_CORPUS=/path/to/corpus.txt PHOTON_EPOCHS=50 PHOTON_BATCH=64 make serious-train
PHOTON_TOKENIZER=wordpiece PHOTON_RESUME=1 make serious-train
#+end_src

The serious loop uses the same dataset loader, checkpoint, epoch eval snapshot,
and saved history path.  Defaults stay small for quick smoke runs, while
~PHOTON_CORPUS~, ~PHOTON_EPOCHS~, ~PHOTON_BATCH~, ~PHOTON_CONTEXT~,
~PHOTON_HIDDEN~, ~PHOTON_LR~, ~PHOTON_CHECKPOINT~, ~PHOTON_BEST_CHECKPOINT~,
~PHOTON_HISTORY~, ~PHOTON_HISTORY_CSV~, ~PHOTON_CHECKPOINT_EVERY~,
~PHOTON_PROGRESS~, ~PHOTON_VOCAB~, ~PHOTON_BACKEND~, and ~PHOTON_MAX_CHARS~
make it usable for minute-scale local corpus experiments.  ~PHOTON_MAX_CHARS~
limits a large source file to a deterministic prefix for rehearsal runs before
using the full corpus.  ~PHOTON_BACKEND~ accepts
~list-vector~, ~elisp-vector~, or ~elisp-tensor~; the default remains
~elisp-vector~.  Batch training selects a validation best checkpoint by
eval total loss, using memory-off fallback accuracy and then eval accuracy as
tie breakers.  Epoch history snapshots and CSV export include eval loss and
~eval_fallback_accuracy_permil~.  Fallback metrics are accumulated in the same
eval pass as loss/accuracy, so larger-corpus validation does not run a second
full readout sweep just to fill history.  Snapshots and CSV also include
~epoch_elapsed_seconds~ and ~total_elapsed_seconds~ for tracking speed changes
across longer runs.  By default
~photon-train-batch-options~ restores that best checkpoint before returning,
rebuilds the target-state clusters on it, and saves it back to the best path,
so an overfit final epoch is not the model kept for later generation.
Current README.org prefix rehearsal snapshot with ~PHOTON_MAX_CHARS=4000~,
wordpiece, context 8, hidden 16, epochs 2, and batch 32: source chars 26503,
used chars 4000, token count 1812, pair count 1804, eval accuracy 24 -> 38
permil, eval total loss 391700 -> 385250, best epoch 1.  Current tiny
wordpiece smoke history records eval fallback accuracy 562 permil in both the
sexp snapshot and CSV, with epoch elapsed seconds also recorded.  The saved
vocab has 477 wordpieces and records source/used character counts in vocab
metadata.

whether generation is becoming more text-like, not a language-quality score.

two tiny train/eval corpus splits, three loss modes, two cache limits, exact

~full-readout~, ~prototype-off~, ~structural-off~, and ~output-head-only~.

  ~raw-anchor-prediction~ 3, raw-anchor margin about 0.087, output-head margin

- Evaluation is read-only: learning-rate 0 paths no longer call update
  routines, so a before-eval pass does not mutate gains/projections before the
  subsequent training run.
- Exact transition memory is controlled by the architecture param
  ~next-token-memory-enabled~.  Setting it to 0.0 gives the memory-off ablation.
- Context-anchor readout is controlled by ~context-anchor-enabled~ and learns
  into ~context-anchor-weight~ when the anchor token supports the target.  The
  learned weight is capped by ~context-anchor-weight-max~ so stream text
  fallback does not let the dense anchor overrule strong suffix n-gram evidence.
  Text fallback also uses a suffix n-gram anchor table controlled by
  ~context-anchor-ngram-enabled~, ~context-anchor-ngram-size~, and
  ~context-anchor-ngram-weight~.  A small contrastive correction controlled by
  ~context-anchor-ngram-contrastive-enabled~ and
  ~context-anchor-ngram-contrastive-weight~ nudges target suffix counts up and
  rival counts down when the next-token margin is weak.
- Text fallback has lightweight structural character-class biases controlled by
  ~char-class-bias-enabled~, ~char-boundary-bias-enabled~,
  ~structural-boundary-bias-enabled~, and ~newline-boundary-bonus~.  Structural
  bias is gated by ~structural-bias-letter-gate-scale~ and
  ~structural-bias-space-gate-scale~ so it does not override a letter-oriented
  base readout.  The exact structural suffix path also has a separate
  ~structural-tie-breaker-weight~ component for repeated space/newline
  ambiguity.
- The output-head path has a small auxiliary margin update controlled by
  ~output-head-aux-update-weight~.  It updates the output head when the
  output-head-only margin is weak even if the full readout is already correct.
  A second anchor distillation update,
  ~output-head-anchor-distill-weight~, updates the output head from
  ~context-anchor-state~ when the anchor top-k contains the target; this is what
  closes the held-out triad output-head-only gap.
- Stream training also has suffix n-gram distillation controlled by
  ~output-head-ngram-distill-weight~ and ~prototype-ngram-distill-weight~.
  When the n-gram anchor ranks the target, the model distills a blended
  state/context-anchor signal into the raw output head and target prototype.
  This directly targets cases where ~ngram-anchor-only~ is correct but
  ~output-head-only~ or ~prototype-only~ misses.
- Wordpiece training adds token length/frequency scaling for output-head and
  target-prototype updates.  Long or still-rare pieces get a bounded update
  boost, controlled by ~wordpiece-long-token-update-weight~,
  ~wordpiece-rare-token-update-weight~, and ~wordpiece-update-scale-max~.  This
  leaves char-stream defaults unchanged while improving subword affine
  readout.
- Stream training now rebuilds a bounded target-state cluster table after the
  final epoch.  The ~output-head-only~, ~state-cluster-only~, and
  ~prototype-only~ ablations use this nearest-state dense readout.  A follow-up
  cluster-teacher distillation pass stores trainable ~output-head-prototype~
  states for ~raw-output-head-only~, while ~linear-output-head-only~ and
  ~raw-prototype-only~ keep the pure affine head and averaged target prototype
  visible as baselines.
- Reconstruction now uses a separate ~reconstruction-head~, so reconstruction
  alignment no longer mutates the next-token ~output-head~.
- ~default-cache~ lowers ~triad~ elapsed-ish steps from 453 to 347 compared with

* Vector Backend

Vector math lives in ~lisp/photon-vector.el~ and is intentionally separated
from the PHOTON model code.  This file is the first candidate for extraction
into a standalone NeLisp/Emacs Lisp vector library.

Vector math goes through a backend alist stored in ~photon-vector-backend~.
Available backends:

- ~list-vector~: plain list vectors, maximum compatibility
- ~elisp-vector~: Emacs Lisp vector storage using ~aref~ / ~aset~
- ~elisp-tensor~: vector-of-vectors matrix/tensor storage with bundled
  tensor add/scale/map/zeros operations

Each backend implements:

- ~add~
- ~scale~
- ~dot~
- ~matvec~
- ~matrix-from-rows~
- ~matrix-shape~
- ~tensor-shape~
- ~tensor-add~
- ~tensor-scale~
- ~tensor-map~
- ~tensor-zeros~
- ~squash~
- ~from-list~
- ~to-list~
- ~fingerprint~
- ~zeros~

Install another backend with:

#+begin_src elisp
(photon-set-vector-backend MY-BACKEND)
#+end_src

External/native backends can be assembled with:

#+begin_src elisp
(photon-make-external-vector-backend
 'native-backend
 '(vector matrix tensor elementwise fingerprint)
 OPERATION-ALIST)
#+end_src

Use the built-in vector backend with:

#+begin_src elisp
(photon-use-elisp-vector-backend)
#+end_src

Use the built-in tensor backend with:

#+begin_src elisp
(photon-use-elisp-tensor-backend)
#+end_src

Compare backend matrix/tensor operations with:

#+begin_src sh
make tensor-benchmark
PHOTON_TENSOR_BENCH_SIZE=64 PHOTON_TENSOR_BENCH_ITERS=500 make tensor-benchmark
#+end_src

Current tiny backend benchmark snapshot at size 24 / iterations 200:
~list-vector~ matvec/tensor elapsed seconds about 0.029/0.256,
~elisp-vector~ about 0.027/0.262, and ~elisp-tensor~ about 0.028/0.227.

This keeps the current NeLisp-compatible list implementation working while
leaving a clear replacement point for a native vector, BLAS, Torch, or future
NeLisp tensor runtime.  Backends expose feature metadata through
~photon-vector-backend-features~ and ~photon-vector-backend-supports-p~.
Matrix and tensor shape/elementwise queries now go through the backend
protocol, so a future native backend can own layout metadata without changing
model code.

* Projection

Layer projections are stored as rank-1 low-rank projection objects by default.
The model applies them through ~photon-model-project~, which caches repeated
projection results inside the model and clears the cache on parameter updates.
Projection cache keys use ~photon-vector-fingerprint~ instead of embedding the
full vector in the key.

The output-head distillation path also owns a separate low-rank
~output-head-projection~.  Distilled output-head prototypes keep raw states, and
readout compares them after applying the current projection, so later projection
updates do not invalidate stored prototype states.

* Cache

The model cache stores repeated token embeddings, chunk/coarse states, full
forward windows, incremental-forward state, and prediction windows.  Cache
entries are model-local and are cleared when trainable state changes, including
output-head rows, embedding rows, architecture scalar parameters, layer gains,
layer projections, target prototypes, and exact next-token transition memory.

Cache usage is tracked in ~cache-stats~.  Use
~photon-model-cache-stats~, ~photon-cache-stats-get~, and
~photon-cache-stats-kind-get~ to inspect global and per-key-kind hit/miss
counts.  Use ~photon-model-reset-cache-stats~ to reset counters without
clearing cache entries.

Cache size is bounded by ~cache-limit~ on the model.  The default is 512 entries.
Use ~photon-model-set-cache-limit~ to change the limit; older entries are
trimmed first.
